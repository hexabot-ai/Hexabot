# Agent Handbook - @hexabot-ai/api

Use this file as the entrypoint for AI coding agents working on the Hexabot API. It summarizes the runtime, module layout, and conventions so changes stay consistent with the NestJS architecture.

## Repository orientation
- Package root: `packages/api` (run commands from repo root with PNPM workspaces).
- Entry point: `packages/api/src/main.ts` -> `bootstrapHexabotApp` in `packages/api/src/bootstrap.ts`.
- App composition: `packages/api/src/app.module.ts` (module imports, static UI serving, global guard).
- Feature modules: `packages/api/src/*` (each folder is a Nest module such as `workflow`, `chat`, `cms`, `user`).
- Extensions: `packages/api/src/extensions/*` (built-in actions, channels, helpers; exported from `packages/api/src/extensions/index.ts`).
- Shared infra: `packages/api/src/config`, `packages/api/src/database`, `packages/api/src/logger`, `packages/api/src/websocket`.
- Shared contract package: `@hexabot-ai/types` (`packages/types/src/*`) for zod schemas and inferred entity output types.

## Runtime architecture
- Global prefix `/api` and body parsing (raw body capture) are set in `packages/api/src/bootstrap.ts`.
- Global pipes: `ValidationPipe` (whitelist + transform) plus `UuidPipe` for UUID params.
- Sessions use `express-session` with a TypeORM-backed store (`SessionOrmEntity`) and Passport session support.
- CSRF protection uses `csrf-sync`, enabled by default with exceptions for auth and webhooks.
- Socket.IO gateway lives in `packages/api/src/websocket`, with Redis adapter when `REDIS_ENABLED=true`.
- Static UI is served via `ServeStaticModule` from `dist/static` or `packages/frontend/dist` when present.

## Configuration and environment
- Env is loaded by `dotenv/config` in `packages/api/src/main.ts`; copy `packages/api/.env.example` to `packages/api/.env`.
- Central config lives in `packages/api/src/config/index.ts`; use it instead of reading `process.env` directly.
- Default port is `3000`, API base URL is `/api`, and SQLite uses `packages/api/hexabot.sqlite` unless overridden.
- DB auto-migration runs outside production or when `DB_AUTO_MIGRATE=true` and `API_IS_PRIMARY_NODE=true`.
- `WORKFLOW_RUN_CLAIM_TTL` (`config.workflow.runClaimTtl`, ms, default 60000) sets how long a workflow run stays claimed by a node that stopped renewing its claim; see "Workflow runs and suspension".
- Cache and Socket.IO Redis support are toggled by `REDIS_ENABLED`; TTL defaults to `CACHE_TTL`.
- Upload settings and signed URLs are controlled by `UPLOAD_DIR`, `UPLOAD_MAX_SIZE_IN_BYTES`, and `SIGNED_URL_*`.

## Database and migrations
- TypeORM config is provided by `packages/api/src/database/typeorm-config.service.ts`.
- Entities typically extend `BaseOrmEntity` (`packages/api/src/database/entities/base.entity.ts`) for UUID + timestamps.
- Migrations live in `packages/api/src/migration/migrations`; module docs in `packages/api/src/migration/README.md`.
- CLI migration commands: `pnpm --filter @hexabot-ai/api run cli migration create|migrate`.
- Seed data runs in non-production via `packages/api/src/seeder.ts` during bootstrap.
- On SQLite, do not use `queryRunner.addColumn`/`dropColumn` on tables other tables reference (e.g. `workflow_runs`): they rebuild the table with `DROP TABLE`, and inside the migration transaction foreign keys stay enforced, so `ON DELETE` actions fire. Use a native `ALTER TABLE ... ADD/DROP COLUMN` there.

## Workflow runs and suspension
- How it works, with five end-to-end examples and diagrams: `src/workflow/README.md`. The points below are the rules that must stay true; keep both in step with the code.
- Three layers host the `@hexabot-ai/agentic` runner (host contract: `packages/agentic/SUSPENSION.md` §8). Each one calls only the layers below it:
  - `AgenticService` (`services/agentic.service.ts`) holds the entry points: inbound events (`handleEvent` for events no one answers, `triggerEvent` for the triggers that answer their caller), `callWorkflow`, the admin operations (`resumeWait`, `cancelRun`), and the choice between waiting for a pass and running it in the background (`WorkflowJobs`). Event and admin resumes share one path: `WorkflowRunExecutor.claimResume`, then `proceedResume`.
  - `WorkflowCallStackService` (`services/workflow-call-stack.service.ts`) carries each run's outcome up its call stack with one loop, `reconcile(runIds, event?)`: a suspended run is resumed with the result of the first child run, on an open `call_workflow` wait, that ended or no longer exists, read from the child as stored (`toEndedCallWorkflowResult`); the run is reconciled again when it suspends, its parent when it ends. A child's result is never handed to its parent. After every pass, `followUps(run, pass)` (`lib/workflow-call-stack.ts`) names the runs to reconcile: the run itself when it is back to `suspended` or refused the payload, its parent when it ended or crashed, none when its claim was lost. `continueResume` runs the pass of a claimed resume, reconciles, and returns the pass. A run that refuses a child's result is failed (`failUnresumable`), since that result cannot be sent again. `reconcile` logs the errors of each run and goes on, so it never rejects; without an event it rebuilds one with `WorkflowEventRestorer`, and a run whose trigger cannot be rebuilt gets its results on its next event or suspension.
  - `WorkflowRunExecutor` (`services/workflow-run-executor.service.ts`) runs one pass of one run under its claim, and knows nothing of parents: `start`, `claimResume`, `resume`, `failUnresumable`. `start` and `resume` share one pass routine (`runPass`): a pass ends as `settled`, `rejected`, `crashed` (the runner threw; the run was failed) or `claim_lost`. It throws only when how it ended could not be written, with the runner's own error when the runner threw; recovery then takes the run over.
- The outcomes of these layers carry a status, not the run: whoever needs the run as stored since reads it back at the entry point (`AgenticService`), once. The types they share (`RunPass`, `ClaimedResume`, `ResumeRefusal`) live in `workflow/types.ts`; a type only one service uses stays in that service (`ResumeClaim`, `UnresumableRun` in the executor).
- Their collaborators:
  - `WorkflowCompiler` compiles the definition a run pins (`compile(run, event)`; `undefined` when none is pinned).
  - `WorkflowRunService` creates runs (`createFromEvent`), claims them and hands out their leases (`RunLease`, `lib/run-lease.ts`), persists runner passes (`persistResult`, `persistCrash`), validates call stacks (`assertCanCallWorkflow`), cancels runs (`cancelSuspended`, `cancelSuspendedDescendants`, `prepareWorkflowDeletion`) and aborts the runs of a closed thread (`hook:thread:postUpdate`).
  - `WorkflowRunRecoveryService` renews the claims held by this process and recovers the runs whose claim lapsed (see below).
  - `WorkflowJobs` (`services/workflow-jobs.service.ts`) runs the work no caller waits for (see below).
  - `lib/workflow-call-stack.ts` holds the pure helpers of parent/child linkage (`resolveRunId`, `getChildRunId`, `getCalledWorkflowId`, `followUps`) and the `call_workflow` payload builders.
- A suspended run persists one JSON `checkpoint` column, the only state needed to resume it; read its open waits with `getOpenWaits` (`packages/api/src/workflow/lib/workflow-run-waits.ts`). `suspendedAt` versions the suspension. `finishedValues`/`failedValues` (`lib/run-lease.ts`) clear the checkpoint.
- Resume order: compile the pinned definition → `validateCheckpoint` (and again with `{ waitId, resumeData }`) before claiming → `WorkflowRunService.claimSuspended(runId, suspendedAt)` → `buildRunnerFromCheckpoint` → `resume({ waitId, resumeData })`. The claim targets the suspension that was loaded (`suspended_at`), not only the status. It returns a `RunLease` (`null` when another caller claimed the suspension first) and writes only the status and the claim, so the run can be put back exactly as it was. `WorkflowRunExecutor.claimResume` does everything up to the claim, `WorkflowRunExecutor.resume` the pass, and `WorkflowCallStackService.continueResume` the pass and the reconciliation that follows; a new run likewise goes through `createFromEvent`, then `WorkflowRunExecutor.start`.
- HTTP requests never wait for a pass: a pass, and the runs it resumes in turn, can take minutes, and a proxy in front of the API (nginx) answers `504` after 60 s. The request answers once the run is claimed and the pass goes on in the background, through `WorkflowJobs.spawn` (`services/workflow-jobs.service.ts`), which logs the errors of the work and tracks it: tests wait for it with `WorkflowJobs.onIdle()`, and `beforeApplicationShutdown` lets it finish for up to 10 s (Nest only calls it on SIGTERM once `app.enableShutdownHooks()` is set, which `bootstrap.ts` does not do yet). Outcomes carry no background work. `AgenticService.resumeWait` returns `accepted` (operator approve/reject/resume answer `202` with the `running` run) and `cancelRun` returns `cancelled`, both spawning what follows; the workflow `postDelete` hook reconciles the callers in the background. Internally `dispatch` claims or creates the run and returns `{ run, proceed }`: `handleEvent` awaits `proceed()` (chat, scheduler), and `triggerEvent` awaits it (MCP, synchronous webhooks) or, with `wait: false`, spawns it and answers with the run (`idle` when created, `running` when resumed; manual runs, webhooks with `?async=true`). A claimed run stays claimed, its claim renewed, until its lease ends, so its pass may wait behind other work. A process that stops during a background pass is covered by recovery like a crash: an admin decision then goes back to the pending list.
- A refused payload leaves the run suspended on the same wait: before the claim nothing is written; after it, the lease settles `putBackValues()`, which puts back the status. Either way `hook:workflow:resume_rejected` is emitted: by the runner for refusals of a step, by `WorkflowRunExecutor.claimResume` for refusals before the claim. How a refusal before the claim is reported depends on the entry point: `handleEvent` returns the run as it is (no one answers a chat message), `triggerEvent` returns `rejected` (or `claim_lost` when another caller claimed the run first; `TriggerEventOutcome`), which `WebhookTriggerService.dispatchTriggerEvent` turns into `422` `payload_rejected` (`409` `claim_lost`) for webhooks, manual runs and the MCP run tool, like the operator endpoints. A refusal during the pass is not reported this way: a caller that waited for the pass (synchronous webhook, MCP) answers with the run back to `suspended`, and the others answered once the run was claimed.
- Claim leases: a run is `idle` or `running` iff it holds a claim (`workflow_runs.claim_id`, lapsing at `claim_expires_at`; both internal, stripped by the run schemas). `createFromEvent` inserts the run already claimed, and `claimSuspended` claims a suspension; both hand out a `RunLease`, held by this process from the claim on, so `WorkflowRunRecoveryService` renews it (one `UPDATE` every TTL/4, without listeners) until it ends. A lease ends once it settles its run (`settle`, even when the write fails) or once its holder gives it up (`end`); its claim then lapses after the TTL, and recovery takes the run over. Whoever claims a run ends its lease, however its work ends: each pass does in `WorkflowRunExecutor.runPass`, cancel and the unresumable fail settle theirs right away. A lease that never ends is renewed until the process stops. The run status lists (`CLAIMED_WORKFLOW_RUN_STATUSES`, `ACTIVE_WORKFLOW_RUN_STATUSES`) and the claim types (`RunClaim`, `ExpiredClaim`, `RunSettlement`, …) live in `workflow/types.ts`.
- Every write of a claimed run goes through its lease (`update` keeps the claim, `settle` gives it back; `persistResult`/`persistCrash` take the lease), with values built by `runningValues`/`suspendedValues`/`finishedValues`/`failedValues`/`putBackValues`, and only applies while the run is still active under its token (`WorkflowRunRepository.updateClaimed`/`settle`); it returns `false` otherwise, and the outcome of the pass is dropped (`claim_lost`; `callWorkflow` throws `WorkflowRunClaimLostError` instead, since its caller expects a result, and rethrows the error of a child's runner that crashed). A `null` token (`WorkflowRunRepository.settle(runId, values, null)`) takes an active run over (thread close only). These writes are query-builder `UPDATE`s: they set `updatedAt` themselves and emit `hook:workflowRun:postUpdate`, which the admin run lists follow.
- Recovery: every node sweeps every TTL/2 for runs whose claim lapsed, once its own queries have succeeded for a whole TTL (so that after a database outage, live nodes first renew their claims). A run with a checkpoint (its resume died) is put back on the suspension it was claimed from: same checkpoint, `suspendedAt`, context and `awaitingOperator`, so an approval is pending again; `hook:workflow:suspended` is emitted, the suspended children its pass called and its checkpoint does not wait on are cancelled, and the run is reconciled. A run whose caller ended, or interrupted 3 times in a row (`recovery_count`), is cancelled instead. A run without a checkpoint (its first pass died) is failed, its suspended descendants cancelled and its parent reconciled. The recovery write re-checks the lapse, so a late renewal wins and each run is recovered once. Steps that ran in the dead pass run again on the next resume. Node clocks must agree within ¾ TTL.
- Inbound events resolve the first open wait not listed in `HOST_RESOLVED_WAIT_REASONS` (`packages/api/src/workflow/types.ts`); the host resolves the others itself (e.g. `awaiting_child_workflow`, resolved by the child run's result through the wait whose `data.workflow_run_id` matches).
- A child's result reaches its parent only while the parent is `suspended`, not while it is still running or claimed by another caller. Every pass that leaves a run `suspended` therefore reconciles it (`followUps`), which delivers the results of the child runs that ended meanwhile. A child and its parent each write their own state, then read the other's, so one of them always sees both and the result is not missed.
- A run that can never resume (missing or drifted checkpoint, no pinned definition) is failed, its parent receives a failed child result, and the event starts a new run. `handleEvent` starts it once that parent went on, so the messages of a conversation keep their order; `triggerEvent` with `wait: false` starts it right away, alongside the parent, so its caller can answer with it. A definition that no longer parses or compiles is not such a case: it depends on the registered actions and binding kinds, so the resume throws and the run stays suspended.
- Actions declare their resume payload with `suspend({ accepts })` instead of validating it and throwing.
- Operator waits (`awaiting_approval` from `await_approval`, `awaiting_resume` from `suspend_workflow`; `OPERATOR_WAIT_REASONS`) are host-resolved: only `WorkflowRunOperatorService` resolves them, behind `PATCH /workflowrun/:id/approve|reject|resume|cancel` (`workflowrun:update`). It builds the payload from the session user (`decided_by`/`resumed_by`, timestamp), so clients never set them; payload shapes live in `workflow/schemas/operator-wait-schemas.ts`. Docs: `src/extensions/actions/workflow/README.md`.
- A resume without an inbound event rebuilds one with `WorkflowEventRestorer` (by `run.workflow.type`; conversational events come from the thread, subscriber, source and channel as they are now, `buildInput()` from the stack root run's input). It throws `WorkflowTriggerUnavailableError` (closed thread, deleted initiator, disabled source or channel).
- `workflow_runs.awaiting_operator` is `true` iff the stored checkpoint holds an open operator wait: `suspendedValues` derives it from `checkpoint.waits`, `finishedValues`/`failedValues` clear it, and claims leave it. `GET /workflowrun/pending` scopes on it (`withAwaitingOperatorScope`, which also requires `status = suspended`).
- A run blocked on an operator (only host-resolved waits, at least one operator wait; `isBlockedOnOperator`) holds the messages of its conversation, but manual, webhook and scheduled events skip it (`findSuspendedRunByInitiator(..., { skipBlockedOnOperator })`) and start a new run.
- Webhook calls run as the workflow's creator (`WebhookTriggerService.trigger`). A call without authentication (`authType: none`) passes `resume: false` to `AgenticService.triggerEvent` (`DispatchOptions.resume`): it never looks for a suspended run and always starts a new one, so an anonymous caller cannot resolve the waits of the creator's runs, or read their output.
- `AgenticService.cancelRun` claims the suspension, marks the steps of its open waits `cancelled`, fails the run, emits `hook:step:cancelled`/`hook:workflow:failure` (all in `WorkflowRunService.cancelSuspended`), cancels its suspended descendants, and reconciles its parent in the background, which receives the failed result.
- Closing a thread (`hook:thread:postUpdate`) runs `WorkflowRunService.abortActiveRunsForThread`: each suspended run of the thread goes through `cancelSuspended` (claimed, waits cancelled, hooks emitted), and idle/running runs are only marked failed, taken over from their pass, whose final write is then dropped. A run whose status changed since it was loaded (claimed or recovered meanwhile) is handled once more from its new status. Child runs share their caller's thread, so no parent is resumed.
- Deleting a workflow deletes its runs (`workflow_runs.workflow_id` is `ON DELETE CASCADE`). `WorkflowRunOperatorService` settles the call stacks around them: on `hook:workflow:preDelete`, `WorkflowRunService.prepareWorkflowDeletion` cancels the suspended runs they called and returns the runs that called them; on `hook:workflow:postDelete` (after the deletion, so a step retry cannot start the workflow again) each caller is reconciled in the background (`WorkflowCallStackService.reconcile`): a suspended caller is resumed with a failed `call_workflow` result, with an event rebuilt by `WorkflowEventRestorer`.
- `reconcile` treats a `call_workflow` wait whose child run no longer exists as a failed child (`Called workflow <id> was deleted`, or `Called workflow run <id> was deleted` when the workflow still exists). This is the safety net for callers the delete hooks could not notify (trigger not rebuildable, a child in flight, runs stranded before this fix): their next event, or their next suspension, fails the call.

## Extensions and dynamic providers
- Built-in extensions live under `packages/api/src/extensions/{actions,channels,helpers}`.
- External extensions are discovered by naming (`hexabot-channel-*`, `hexabot-action-*`, `hexabot-helper-*`) and compiled `dist/extensions`.
- Dynamic providers are resolved during bootstrap via `nestjs-dynamic-providers` before app creation.
- Extension cleanup runs on application bootstrap in `packages/api/src/extension/extension.module.ts`.
- Use extension settings instead of hardcoded behavior when adding new channel/action/helper behavior.
- An action's `workflowTypes` is enforced, not only a catalog filter: `WorkflowVersionService` refuses (`400`) a version whose tasks use an action its workflow's type cannot run, and `WorkflowCompiler` refuses to compile one, which covers versions saved before that check (`assertTaskActionsSupported`, `src/workflow/lib/workflow-definition.ts`). An action without `workflowTypes` runs in any workflow.
- Channel/helper runtime setting group keys and settings hook namespaces must match the extension `name` (kebab-case).

## Coding conventions and gotchas
- All new TS files must include the license header; ESLint `header/header` enforces it.
- Path alias `@/` maps to `packages/api/src` (see `packages/api/tsconfig.json`); avoid relative path ladders.
- ESLint enforces import ordering and disallows `console.*`; prefer `LoggerService`.
- DTO validation relies on class-validator + `ValidationPipe` (whitelist + transform); keep DTOs in sync with entities.
- Keep API output contract changes aligned with `@hexabot-ai/types` schemas and update `packages/types/README.md` when exported contracts change.
- Chat contract rule: use discriminator-based contracts from `@hexabot-ai/types` only.
- Swagger docs are available at `/docs` in non-production or via `pnpm --filter @hexabot-ai/api run doc`.
